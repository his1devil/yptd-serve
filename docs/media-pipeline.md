# 媒体管线规格：图片、附件、头像、缩略图、本地缓存

定稿于 2026-09-19。读者：iOS（`yptd-mobile-app`）、桌面（`yptd-desktop`）、服务端三边的实现者。
本文自成一体；背后的审计数据见文末「依据」。消息里附件的基础结构见 `client-api.md` §6，
本文是它的扩展，冲突处以本文为准。

## 0. 三条决定一切的事实

1. **出口 ~260 KB/s，入口 ~3.3 MB/s，12.5 : 1。** 出口是全站共享的硬总量，并发下载不增加
   吞吐。结论：上传多花的字节几乎免费，下载省的每个字节要乘以接收人数。所以**能在发送端
   做的事都在发送端做**。
2. **每次取对象有 ~0.5 s 与体积无关的固定开销**（`/object/` 一跳 + MinIO 一跳）。小对象是
   延迟受限，大对象是带宽受限，两者的优化手段不同。
3. **服务器是历史的真相**（OpenIM 存全量）。设备上的一切——消息库、图片、视频——都是可以
   丢、可以重建的缓存，按缓存来管：有上限、可清、按账号隔离。

## 1. 已拍板的产品决定

| 事项 | 决定 |
| --- | --- |
| 发图 | 默认压缩；输入框有「原图」勾选，勾了才额外上传原文件 |
| 档位谁生成 | **发送端**。`ex` 里显式带各档地址，接收端不再拼 URL 参数 |
| 退出登录 | **保留**本地消息库和缓存（下次登录秒开）→ 缓存必须按账号分目录；存储管理页提供「清除此账号的本地数据」 |
| 访问控制 | 先做不可猜的对象名 + 签名地址不出服务器；登录鉴权以后再做 |

## 2. 协议：`ex` 里的附件（rich v2）

```jsonc
{"yptd":"rich","t":0,"a":[{
  "k": "i",                    // i 图片 / v 视频 / f 文件。桌面端原来没有 v，要补
  "u": "https://…/object/<uid>/<id>.jpg",   // 主文件：压缩后的图 / 视频 / 文件
  "n": "设计稿.png",            // 原始文件名，只用于展示；对象名里不再出现
  "m": "image/jpeg",           // mime。新增——接收端不该靠扩展名猜
  "s": 213004,                 // u 指向的那个文件的字节数
  "w": 2048, "h": 1365,        // u 指向的那个文件的像素尺寸（不是原图的）
  "th": {"u": "https://…", "w": 720, "h": 480, "s": 48213},   // 缩略档。新增
  "o":  {"u": "https://…", "w": 6048, "h": 4032, "s": 5127557}, // 原图，勾了「原图」才有。新增
  "b": "1QcSHQRnh493V4dIh4eXh1h4kJUI",   // ThumbHash，base64，≤ 40 字符。新增
  "p": "https://…",            // 视频封面（JPEG，长边 720）
  "d": 12.4                    // 视频/语音时长，秒
}]}
```

兼容规则：
- 不认识的键一律忽略；`th` 缺失（老消息、老客户端）时退回 §5 的服务端按需缩图。
- `w/h/s` 的语义统一为「**`u` 指向的那个文件**」。iOS 现状已符合，桌面要改（现在填的是原文件）。
- `b` 解不出来就画纯色占位，不报错。

## 3. 发送端：压缩与档位

三端参数必须一致——同一张图从哪端发出去，接收方看到的应该一样。

### 图片

| 档 | 规格 | 用途 |
| --- | --- | --- |
| `th` | 长边 720；照片 JPEG q72；源是 PNG 且 PNG 结果更小时用 PNG | 消息流里显示的就是它，**不再升级到主图** |
| `u` | 长边 2048；照片 JPEG q82；**源是 PNG 时保持 PNG**（截图和设计稿转 JPEG 会糊字、透明底变黑），PNG 超过 1.5 MB 才转 JPEG q85 | 点开大图 |
| `o` | 原文件，一个字节不动 | 勾了「原图」才上传；接收端显示「查看原图 (4.8 MB)」，点了才下 |

- HEIC 一律转 JPEG。GIF 原样上传（`m: image/gif`），`th` 取首帧。
- 重编码天然丢掉 EXIF（含 GPS），这是要的。**`o` 保留 EXIF**——「原图」的语义就是原样，UI 勾选处要写明。
- 缩放必须走降采样解码（iOS `CGImageSourceCreateThumbnailAtIndex`，桌面主进程 `nativeImage`），
  不许整图解码后再缩。iOS 头像选图那处 `UIImage(data:)` 是现存唯一的反例，48MP 照片峰值 ~212 MB。
- ThumbHash 在生成 `th` 时顺手算（输入缩到 ≤100px）。

### 头像

640×640 方形裁切，JPEG q88（iOS 现状）。桌面端现在传原图（线上最大 2.36 MB），要补裁切和压缩。
OpenIM 的 `faceURL` 只有一个字段，所以头像的小尺寸继续走 §5 的服务端按需缩图，档位只有 64 / 128 / 256。

### 视频

- iOS：**按码率**决定是否重编码——源码率 > 2 Mbps 或长边 > 1280 就转 720p / ≤1.5 Mbps H.264。
  现状只看分辨率和体积，线上有 12 秒 13.79 MB（8.9 Mbps）的视频，下载 55 秒才能看 12 秒。
- 桌面：不引入 ffmpeg（+70 MB），不转码。上限 100 MB，超过 10 MB 时在发送前提示
  「接收方下载约需 N 秒」。封面 `p` 和时长 `d` 用渲染进程的 `<video>` + canvas 生成。

### 上传用的 hash

OpenIM 秒传去重用的 `hash` **不是文件的 MD5**，而是「各分片 MD5 的十六进制用逗号连起来，再做一次
MD5」；单片文件就是 `md5(md5hex(data))`。三端 SDK 都这么算，所以同一个文件从哪端传都能秒传。
自己调上传接口时拿文件 MD5 当 hash，PUT 会成功，到 `complete_multipart_upload` 才报
`md5 mismatching`（服务端 `openim.Client.Upload` 踩过）。

### 对象名

`<userID>/<128 位随机 id，base32>.<ext>`。`<userID>/` 前缀是 OpenIM 强制的。原始文件名只进 `n`。
桌面端头像现在用裸文件名（`/object/tuitest/bepo.jpeg`）：可猜，且同名重传原地覆盖、URL 不变，
各端缓存永久停在旧头像。

## 4. 接收端：取图、排队、本地缓存

### 取哪一档

| 场景 | 取 |
| --- | --- |
| 消息流 | `th.u`；到达之前画 `b`（ThumbHash），框按 `th.w/h` 预留 |
| 点开大图 | `u`；`o` 存在时显示「查看原图 (大小)」 |
| 老消息（无 `th`） | §5 的按需缩图，`s ≤ 512 KB` 直接取 `u` |

### 下载排队（两端同一策略）

- 小对象（头像、`th`，预期 < 100 KB）：并发 3。它们是延迟受限的，并发有收益。
- 大对象（`u`、`o`、视频、文件）：**串行**。管子是总量限速，并发只会让所有图一起慢。
- 视口内优先；滚出视口的请求取消；预取只取下一屏的 `th`。

### 本地缓存

服务器是真相，所以这里全是缓存，但要当一等公民来做：

- **键 = 对象路径 + 变体**（如 `u_x/ab12.jpg#th`），不含 host、query、签名。
- **按账号分目录**：`<cache>/<userID>/…`。退出登录保留，换账号互不可见。
- **三个池子，各自 LRU**，互不挤占：

  | 池 | 默认上限（iOS / 桌面） | 内容 |
  | --- | --- | --- |
  | avatars | 50 MB / 50 MB | 头像各档。永不被聊天图挤掉 |
  | images | 500 MB / 1 GB | `th`、`u`、`o` |
  | files | 1 GB / 2 GB | 视频、文件。最先淘汰 |

- **增量淘汰**：写入后超限就按最后访问时间删到 80%。iOS 现状只在冷启动剪一次。
- **发送即入缓存**：上传成功后把本地字节按远端键写进缓存。自己发的东西永不再下载
  （iOS 的 `aliases` 现在只在内存里，重启即失效）。
- **视频落盘**：首次下完存 files 池，之后本地播。iOS 现状是 `AVPlayerItem(url: 远程)`，每看一次重下一次。
- 内存层：只放解码后的位图，键带**量化后的**像素档（iOS 现状不量化，同一头像 5 个尺寸解码 5 次）。
  大图查看器解码上限 1600px（现状 3000px，两张就挤爆 64 MB 内存缓存）。
- 桌面端不再依赖 Chromium HTTP 缓存：主进程 `protocol.handle` 接管媒体请求，落上述缓存目录。
  排队、以后的鉴权头也在这一层做。

### 消息与内存

- SDK 的 SQLite 消息库不动：300 条 ≈ 0.8 MB，多年内不是容量问题。
- 内存里的时间线做 LRU：当前会话 + 最近 5 个，各留 200 条；其余淘汰，回来时从本地库重读（毫秒级）。
  iOS 的 `rawMessages` 跟着一起淘汰（现状无上限）。
- 从通知进入：等 `ex.msg_id` 那条同步到本地再跳，超时 500 ms 就直接进。

### 存储管理页（两端）

显示 消息库 / 头像 / 图片 / 视频与文件 各占多少；每池一个清除按钮；上限可调；
「清除此账号的本地数据」（消息库 + 全部缓存）——退出登录不删，共用电脑的人用这个。

## 5. 服务端

### nginx：内部跟随 302（第一阶段，不需要发客户端版本）

现状：`/object/…` 回 302 到一个**每次都重新签名**的 MinIO 地址。地址每次都变，桌面端 Chromium
缓存按 URL 做键，命中率 0——实测 902 条缓存记录只指向 39 个对象，88% 是重复下载。

改成 nginx 在内部跟随这个 302（`proxy_intercept_errors on; error_page 302 = @follow;`），
客户端看到的是**稳定地址上的 200**：
- 透传 MinIO 的 `ETag` / `Last-Modified`，加 `Cache-Control: private, max-age=86400`。
  对象按内容寻址，过期后一次 304 重校验即可。
- 每个对象少一次往返（~0.25 s）。
- 签名地址不再离开服务器（现在是 7 天有效的外泄凭据）。
- `Range` 要透传（视频拖动）。

同时：`limit_req` 限住带 `type=image` 的请求——每个新的宽高组合都会让 OpenIM 读原图、解码、
写一个永久缩略图对象，现在无鉴权无限流。

### 按需缩图（只为老消息和头像保留）

`/object/<name>?type=image&width=W&height=H&format=F`，三个坑：
- `format` 不传就是 **PNG**：照片的缩图比原图还大（实测 102 KB 的 JPEG，960 档 873 KB）。
  规则：**format 跟源文件走**，源是 jpeg/heic 传 `jpeg`，源是 png 传 `png`。
- `width` 或 `height` > 1024 **静默回原图**，不报错。
- 画质是 q75 + 最近邻，只适合小档。

### 其他

- `/etc/hosts` 把 `im.zhanghuanyang.com`、`im-file.zhanghuanyang.com` 指到回环：服务器上按域名取
  自家对象的进程（Dummy 的 `yptd-note`）现在走公网回环，15.5 s vs 0.04 s，还占全站出口。
- 以后：缩略图目录的 lifecycle、过期清理（上游 cron 里删文件那段是注释掉的，`fileExpireTime` 是死配置；
  按实测 7.5 MB/天，21 GB 余量 15 人约 3 年、50 人约 11 个月）、GET 鉴权。

## 6. 分阶段

| 阶段 | 内容 | 要发版吗 |
| --- | --- | --- |
| **1** | nginx 内部跟随 302 + 缓存头 + `limit_req`；hosts 回环 | 不用 |
| **2** | 两端：按需缩图带对 `format`；桌面：上传前压缩、随机对象名、头像裁切、认 `k:v`/`p`/`d`/`m`；iOS：头像降采样、缓存增量淘汰、视频落盘、视频按码率转码 | 各一版 |
| **3** | `th` / `o` / `b` 协议 + 「原图」勾选；缓存重做（三池、按账号、发送即入）；桌面 `protocol.handle`；下载排队；存储管理页；时间线内存 LRU | 各一版 |
| **4** | GET 鉴权；lifecycle 与过期清理 | — |

阶段 2 和 3 的新字段对老客户端都是「忽略未知键」，可以任意顺序上线。
